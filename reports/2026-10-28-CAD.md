# CAD 调研与实验进展汇总

整理日期：2026-10-28。覆盖 10 月 22 日起的调研，以及 10 月 27–28 日完成的实验。模型名称采用实际路由名，所有实验 reasoning effort 均为 high。

## 这阶段推进了什么

这阶段把 CAD 工作从文献调研推进到了真实环境评测：在约定的 10.9 物理机上跑通了 CADDesigner 的程序化建模、执行和视觉反馈，并完成 CADTestBench 抽样、全量及失败题恢复实验；随后用 BenchCAD 官方 harness 跑了九个公开开发样例，比较 Luna、Terra 和 Astra。累计保存 **433 个正式 episode、11,370 次成功返回的模型调用**，结果、代码、产物和完整轨迹均已归档。

CADTestBench 上，Luna/high 的 abstract 全量原始通过率为 **69.5%**；统一修复评分适配器的 NumPy 作用域后为 **72.0%**。针对未通过题再用 Terra/high 生成，累计覆盖达到 **176/200（88.0%）**。这个 88% 使用历史评测结果选择补跑题，并对多次生成取成功并集，不能写成单模型单次通过率，也不是已验证可部署的路由效果。

BenchCAD 九题上，Astra/high 全部形成可评分产物，逐题均分 **0.4687**，高于 Terra 的 **0.1723** 和 Luna 的 **0.1274**；与另外两者逐题比较均为 7 胜、2 平。但 Astra 成功调用达 220 次，已知用量按 API 价格折算约 $100.10，成本显著增加。这批是公开开发样例的原生本地试跑，不能代表 Core 正式成绩。

当前判断是继续以**程序化 CAD、可执行验证和修复数据**为主线。已完成的是环境、评测和轨迹积累；自有 student 训练、类型化计划 P 的对照实验、Harbor 迁移和 BenchCAD Core 评测尚未完成。

## 一、CAD 调研：任务、Agent 和模型需要分开看

我们把相关工作按三层整理：benchmark 定义输入、环境、预算和验收；Agent/harness 组织工具、状态、执行与修复；模型决定下一步代码或动作。带图片输入或渲染反馈不等于 GUI 操作，Docker/Harbor 也不等于某种交互方式。

[完整调研原文](../references/CAD-survey-2026-10-22.md)还保留 Text2CAD-Bench、CADBench、CADGenBench、IterCAD-Bench、DeepCAD 和 Fusion 360 等工作及来源。其发布状态与公开榜单是 **2026-10-22 的历史快照**；本汇总重新核对了上表的主要论文/项目入口，并用下文更新本地实验状态。

## 二、CADDesigner × CADTestBench 实验

### 2.1 数据、指标和运行方式

abstract 主要描述形体、关系和比例，detailed 提供更多明确尺寸；相同题号分别使用各自分区的 CADTests，测试项并不完全相同。**PR** 是通过该题所有 CADTests 的题目比例；**RS** 是先按题内 requirement group 汇总、再按题平均的需求得分，不能用总检查通过数直接代替。

运行采用 10.9 物理机的原生 Python/CadQuery/Redis 和 CADDesigner 工具链，CPU 建模、离屏渲染，模型推理由远端服务提供。模型通过现有 Codex 账号桥接，认证留在开发节点。批次通常为 10 并发，每题至多 60 次模型请求、1,200 秒，主工具与 specialist 分别有 40/24 次上限；所有 LLM 角色固定到对应模型/high。单题 pilot 的实际配置单独保留。

生成结束后再引入本批评分表；提交适配器只导入选定的原始 STEP 为 `final_result`，不人工修几何，不把最终 CADTests 结果反馈给 Agent。提示和目录组织限制答案访问，但没有操作系统级防泄漏沙箱。这是带已归档适配补丁的实验配置，不是未修改的上游默认成绩。

分层 30 题没有官方难度标签：只按原始提示的操作、特征和关系构造复杂度代理，将 200 题分成 67/67/66 三档，各抽 10 题，并兼顾基础形体、多部件、曲线/圆角、孔槽/空腔四类。种子和清单在生成前冻结，不读取测试或历史分数决定采样，不能把该代理当作人工标注难度。

v2 只统一为评分适配器补上 `import numpy as np`，解决部分测试依赖提交作用域中 `np` 的问题；STEP、模型输出、测试代码和阈值均未改变，没有新模型调用。两份结果独立保留。对应 RS：Terra30 为 **96.8782%→97.8849%**，Luna200 为 **93.0188%→93.5056%**，Terra56 为 **88.7292%→89.4945%**。

### 2.3 累计恢复结果怎么理解

在统一 v2 口径下：**Luna 144/200 → Terra56 新补回 23，累计 167/200 → 固定剩余 33 题各新增 3 次，再补回 9，累计 176/200**，剩余 24 题。

33 题的三轮全部跑完，前一轮成功也不停题；每次从原始 abstract 提示重新生成，不沿用失败代码、产物或失败检查项。三次新尝试中通过 0/1/2/3 次的题数分别为 **24/6/2/1**。探索性的 Terra10 和 Terra30 不计入这条累计路径。

这是由离线评分选择失败题、统计成功并集的**条件恢复实验**，不是 Terra 全量 pass@1/pass@3，也不能直接视为自动级联系统的上线准确率。

### 2.4 论文结果对照

[CADTestBench 论文 v1，Table 3](https://arxiv.org/html/2605.07807v1#S5.T3)中，Claude 4.6 Sonnet + CADTests+Log 的 abstract **PR 81.0%、RS 96.2%**，detailed **PR 62.5%、RS 89.7%**；同模型 ReAct 的 abstract PR 为 71.5%、detailed 为 58.0%。这是论文报告，未按其方法本地复跑。

论文 CADTests+Log 使用模型基于提示生成的检查和日志，不是将官方最终评分测试交给 solver。我们的模型、CADDesigner harness、预算、STEP 导入方式及 v2 评分适配均不同，不能用小样本 86.67% 或多阶段累计 88% 宣称刷新论文单次全量成绩。

### 3.3 环境与校准边界

这批使用 **BenchCAD 官方 harness 2.1**，没有使用 CADDesigner。运行方式为官方提供的 `CADENV_LOCAL=1` 原生子进程模式，没有采用固定 Docker 合同。OpenAI SDK 2.29.0 也低于该源码声明的 3.16 下限，实际可运行不能等同依赖完全对齐。

九题参考提交都得到可计算分数 1.0，但 T2-case1 仓库 round-trip 记录为 0.996616，差异超出原容差 0.0001。因此保留 **contract_aligned=false**，不放宽容差或改参考分数。Astra 启动前核对源码、输入哈希和依赖不变后复用 Terra 的九题参考校准，未重新跑参考评分或复用模型答案。

Astra 共 225 次请求：220 次成功、有 usage 的模型调用；3 次在终结响应前中断，2 次返回服务器过载的失败终结响应且 usage 为空，官方 SDK 按原有机制重试。9 题最终都有评分。归档明确区分 222 份终结响应与 220 个成功 step，并保留失败流、错误和全部未知用量，不把失败响应当成功调用。

Astra 九题累计输入 **11,225,097 token**，其中缓存命中 **2,782,976**，输出 **257,874**；多轮输入回放使成本远高于 Terra 的九次调用。其单调用最大输入 119,112 token。这里只说明本次工作流的实际消耗，不能把单位 token 的价格倍数当成所有 CAD 任务的完成成本倍数。

## 五、具体案例和研究判断

**评分环境问题与模型失败需要分开。** Terra30 中三个案例各有一项检查因 `np` 未定义失败，统一适配后相同 STEP 通过，因此 PR 从 23/30 变为 26/30；这支持修评分环境，不能解释为模型经修复后能力上升。

**有些零分来自验收选择或描述冲突。** 配对样例 abstract-00670457 的检查器按面积选最小平面，事后测量发现它选到了侧面，实际挤出端盖面积相等；detailed-00984833 同时存在“上层更窄”和数值宽度相反、总高度与测试目标冲突的问题。原始失败均保留，尚未把它们认定为全部应改分的 benchmark 错题。[诊断与数值证据](https://github.com/cai-yutao/CAD-agent/blob/6c45380541c2480bf6695f8aa87bf705fa893a72/docs/experiment-report.md)

**复杂装配与生成合法零件是两回事。** BenchCAD T4-case1 三模型总分都为零；Astra 的零件子项有分，最终装配仍未拿分。T2-case2 则从 Terra 的 0.0235 提升到 Astra 的 0.7795，但 Astra 为该题成功调用 46 次，另有失败重试。下一步需要分析空间放置和轮次收益，而不是只收集“能导出 STEP”的正例。

结合调研，当前更有价值的切口是：**在有对象引用和跨步骤依赖的长计划上，局部修复能否减少对已正确部分的破坏，并在相同预算下优于完整重写。** 这是待验证假设；“专用 API + 执行反馈 + SFT/RL”的组合已有直接相关工作，不能仅凭架构组合认定创新。

## 六、下一步建议（尚未启动）

1. 从失败轨迹中区分规格歧义、验证器/适配问题、构造错误、引用错误和装配放置错误，先建立 30–50 个可人工复核的开发实例；按源 CAD identity/几何家族划分，避免同一模型不同描述跨训练测试泄漏。
2. 固定模型、工具、反馈权限和总预算，对比自由 CadQuery 与类型化计划 P，再分别对比无反馈重试、有反馈整段重写、受保护局部修复，报告需求通过率、回归率及每个合格样本成本。
3. 只有真实执行和需求验证通过的计划进入正确标签；失败及“无法验证”单独保存。现有代码轨迹到 P 的转换质量需先检查，再决定 student 和 SFT 规模；当前没有 student 训练结果。
4. 若继续做正式 benchmark，对 BenchCAD 先解决固定 Docker/依赖与参考校准差异，再确认 Core 访问；对 Harbor 可优先检查 Parametric CAD Bench V3。正式评测沿用独立任务集，不把当前开发样例训练后成绩当泛化证据。
